# Hosting 사용량과 AdSense 재검토 준비 계획

> 상태 주의: 이 문서는 2026-09-08 작업 재개 전의 조사·계획 기록이다. 최신
> 실측과 완료/미완료 구분은 `EXECUTION_STATUS_20260908.md`를 우선한다.

점검일: 2026-09-08 KST. 대상: Mesu-Gak (`studio-5459225470-8cee2`), 공개 사이트 `https://mesu-gak.web.app`.
이 문서는 읽기 전용 실측과 실행 계획이다. 이 계획으로 광고 활성화, 재심사 신청, 요금제 변경을 실행하지 않았다.

## 1. 실제 사용량과 비용 해석

| 항목 | 확인값 | 해석 |
|---|---:|---|
| 도메인별 이번 달 전송량 최신 표본 합계 | 2,769,768 bytes, 약 2.77 MB | 서로 다른 시각의 누적 표본 합계이며 실시간 청구값 아님 |
| mesu-gak 최근 24시간 전송량 | 278,879 bytes, 약 0.279 MB | 조회 구간 Monitoring DELTA 합계 |
| 프로젝트 Hosting 저장량 합계 | 17,462,132 bytes, 약 17.46 MB | Hosting 무료 저장량 10 GB보다 매우 작음 |
| Firestore 저장량 최신 표본 | 6,332,808,899 bytes, 약 5.90 GiB | 무료 1 GiB 초과. 방문자가 없어도 저장 비용 가능 |
| 결제 상태 | Blaze, billingEnabled=true | Spark 전환 승인은 받았으나 정리·점검 후 전환 조건은 아직 미완료 |

Hosting 트래픽이 현재 비용의 주원인이라는 증거는 없다. Hosting 바이트 지표로 방문자 수나 모든 API 요청 수를 알 수는 없다. Firestore 읽기·쓰기·저장·전송은 별도다. 최근 확인한 Firestore 24시간 읽기는 78,844건으로, 프런트엔드 방문뿐 아니라 작업·관리·정리 요청이 섞인다. 이 값을 웹 방문 횟수로 해석하면 안 된다.

실측 원본은 로컬의 무시된 runtime/hosting-audit.json, runtime/site-measurement.json에 있다. Monitoring 표본에는 지연이 있고 일부 도메인 표본은 오래되었다.

## 2. 방문량별 Hosting 예상

gzip 응답 본문과 현재 번들 의존성을 측정했다. 브라우저 캐시가 전혀 없는 최초 로딩 기준이며 실제 방문자 수와 같지 않다.

| 경로 | 1회 파일 전송 | 360 MB/일 기준 | 10 GB/월 기준 |
|---|---:|---:|---:|
| 홈·학습 진입 | 104,311 bytes | 약 3,450회/일 | 약 95,900회/월 |
| 분석 화면 진입 | 233,455 bytes | 약 1,540회/일 | 약 42,800회/월 |

공식 가격표는 무료 전송을 360 MB/일로, Hosting 사용량 안내는 10 GB/월로 표시한다. 두 안내가 일치하지 않으므로 계획에서는 일별 360 MB와 월별 10 GB를 모두 관리하고 실제 콘솔 적용 한도를 확인한다. Blaze 초과 전송 가격은 두 안내 모두 $0.15/GB다. 이 표는 기존 트래픽이 없다는 가정으로 무료 전송량을 나눈 용량 추정이지 청구 보증이 아니다.

예를 들어 분석 최초 로딩 1,000회는 약 233 MB다. 응답 헤더, 추가 파일, 이미지 증설, 재배포, 봇, 다른 Hosting 사이트 사용량 등의 여유를 별도로 둔다. Firestore API 응답과 외부 광고 파일은 위 번들 측정에 포함되지 않는다. 브라우저 캐시 재사용은 전송을 줄이지만 Firebase CDN 캐시에서 내려가는 바이트도 사용량에 포함된다.

현재 공개 분석 첫 기본 조회는 통상 문서 2개를 읽고, 15분 세션 캐시 적중 시 반복 조회를 줄인다. 검색·다른 페이지·관리 작업은 추가 읽기를 발생시킨다. 무료 읽기 50,000건을 2로 나눈 25,000회는 다른 읽기가 전혀 없는 이론값일 뿐이다. 클라이언트 제한과 지연된 모니터링만으로 Blaze 전체 과금을 차단할 수 없다.

## 3. 배포 사이트에서 확인한 개선점

- 6개 학습 글과 방법론·소개 페이지가 이미 있다. 콘텐츠가 전혀 없는 사이트는 아니다. 다만 글이 짧고 자동 분석 설명이 반복되어, 원래의 해설과 이용자에게 주는 가치 보강이 필요하다.
- 배포 HTML의 게시자 메타 ID는 예시 `ca-pub-1234567890123456`이고 ads.txt는 `pub-5493583869107151`이다. AdSense 계정의 실제 게시자 ID와 제출 도메인을 확인하여 일치시켜야 한다.
- 학습 글에 “광고 공간 / AdSense 승인 후 실제 광고가 표시됩니다”라는 준비 중 표시가 보인다. 실제 광고는 현재 비활성화되어 있다. 이 표시 자체가 반려 원인이라고 단정할 수는 없으나 완성된 본문에 불필요하다.
- /learn/rsi의 초기 HTML에는 본문이 없고 JavaScript 실행 후 렌더링된다. JavaScript 사이트라는 이유만으로 부적격은 아니지만, 정적 HTML 본문은 크롤러와 직접 방문의 안정성을 높인다.
- /robots.txt와 /sitemap.xml이 200 text/html SPA 화면을 반환한다. 존재하지 않는 경로도 200으로 분석 화면에 연결된다.
- 초기 HTML 제목·설명은 공통이고 개별 글의 검색 진입 정보가 부족하다. 소개 화면의 설정되지 않은 후원 링크도 정리 대상이다.
- 실제 Google 심사 시점·제출 URL·계정 세부 사유는 확인하지 못했다. 위 발견을 반려의 확정 원인으로 단정하지 않는다.

## 4. 변경 순서와 완료 기준

### 단계 1 — 사이트 검증과 미완성 표시 정리

대상: frontend/index.html, 광고 환경변수와 빌드 검증, AdSenseSlot, 소개 페이지.

1. AdSense에 제출한 정확한 도메인과 계정 게시자 ID를 확인한다.
2. 메타 태그와 ads.txt를 실제 계정에 맞춘다. 광고가 꺼져 있어도 프로덕션에 예시 ID가 있으면 빌드가 실패하도록 한다.
3. 광고 준비 중 표시와 동작하지 않는 링크를 제거한다.
4. 소유권 확인과 광고 게재를 분리한다. 계정 승인 상태를 임의로 true로 바꾸지 않는다. 승인 전 실제 광고는 계속 끈다.

완료 기준: 게시자 ID 일치, 유효한 ads.txt, 미완성 표시 없음, 광고 요청 없음. 소유권 확인은 Google이 지원하는 메타 태그 또는 ads.txt 방식으로 가능하다.

### 단계 2 — 기존 콘텐츠를 읽을 이유가 있는 학습 자료로 보강

대상: LearningPages와 학습 콘텐츠, 방법론·소개·법적 고지.

1. 기존 6개 글 각각에 정의, 수치 계산 예제, 직접 만든 도표, 해석 과정, 실패하는 경우, 한계, 출처를 넣는다. 분량 채우기와 표현만 바꾼 반복을 피한다.
2. 사람이 검토한 사례 해설 4~6개를 초기 편집 목표로 잡는다. 이는 Google의 최소 글 수가 아니다. 성공 사례뿐 아니라 잘못된 신호와 손실 가능성도 설명한다.
3. 방법론에 실제 코드의 점수 구성과 예시 계산을 연결한다. 현재 사용하지 않는 지표나 데이터가 있는 것처럼 설명하지 않는다.
4. 공공데이터포털의 실제 사용 API·갱신 시각·누락 처리·이용 조건을 코드와 대조해 명시한다. 다른 제공자와 혼동하지 않는다.
5. 실제 작성·검토 주체와 수정일, 문의 방법을 표시한다. 자격이나 성과를 꾸며내지 않는다.
6. 홈은 링크 카드 외에도 서비스의 교육 목적, 대표 해설, 읽는 순서, 분석의 한계를 설명한다.

완료 기준: 각 글이 차트 도구를 실행하지 않아도 독립적으로 유익하고, 설명과 수치가 검증된다. 종목마다 같은 문장을 복제해 대량 생성하지 않는다. Google이 보장하는 글 수·글자 수 공식은 없다.

### 단계 3 — 추가 서버 비용 없는 정적 글 제공

대상: Vite 빌드, App 라우팅, public 파일, firebase.json.

1. 현재 React/Vite와 Firebase Hosting을 유지하면서 학습·사례·소개 페이지를 빌드 시 HTML로 생성한다. 상시 SSR 서버나 Cloud Functions는 추가하지 않는다.
2. 각 페이지에 고유 제목·설명·canonical과 본문을 제공한다. JavaScript 초기화 이후에도 정상 동작하는지 확인한다.
3. 진짜 robots.txt와 sitemap.xml을 만들고 공개 완성 글만 사이트맵에 넣는다.
4. 알려진 앱 경로만 허용하고 존재하지 않는 URL은 실제 HTTP 404로 반환한다. 대표 도메인을 정하고 다른 도메인 처리는 기존 이용 경로 확인 후 정리한다.
5. 해시 자산 장기 캐시는 유지하고 HTML 캐시 규칙이 실제 페이지 경로에도 적용되게 한다.
6. 학습 글은 Firestore를 조회하지 않게 유지한다. 분석 도구는 지연 로딩과 기존 캐시를 유지한다.

완료 기준: 직접 URL 접근의 초기 HTML에 본문이 있고, robots·sitemap MIME과 404 상태가 정확하다. 새 이미지 포함 최초 전송량을 다시 측정한다. 공개 분석 JSON 정적화는 Firestore 읽기를 Hosting 전송량으로 옮기는 선택이므로 별도 비용 계산 후 결정한다.

### 단계 4 — 광고 가능한 화면을 좁혀 설계

1. 처음에는 완성된 학습·사례 본문만 광고 허용 목록에 넣는다.
2. 로딩·빈 결과·오류·로그인·관리·검색 조작 화면과 검토하지 않은 자동 분석 화면에는 광고를 넣지 않는다.
3. 초기 배치는 본문 뒤 수동 광고 1개를 제안한다. 이는 모바일 사용성과 검증을 위한 설계 선택이며 Google의 의무 개수 제한은 아니다.
4. 버튼과 광고의 터치 영역을 충분히 분리하고 광고 때문에 내용이 크게 밀리지 않게 한다. 승인 직후 자동 광고를 전 화면에 일괄 적용하지 않는다.
5. 대상 지역에 필요한 동의 관리와 개인정보 고지를 맞춘다. EEA·영국·스위스 이용자 광고에는 Google 인증 CMP 요건을 적용하고 동의·거부·철회 흐름을 검증한다.

완료 기준: 허용 본문 외 광고 요청 0, 동의 조건 충족 전 광고 요청 0, 실제 계정 승인 후에만 운영 게이트 활성화. 구조상 데이터가 있다는 코드 검사만으로 콘텐츠 품질 승인을 대체하지 않는다.

### 단계 5 — 모바일·크롤러 확인 후 재검토 신청

1. 320px·390px 및 데스크톱에서 직접 진입, 메뉴, 뒤로 가기, 본문·표·도표, 링크를 실제 브라우저로 확인한다.
2. 가로 넘침, 작은 터치 대상, 본문을 가리는 요소, 콘솔 오류를 수정한다.
3. 로그아웃 방문에서 전체 글이 읽히고 초기 HTML·canonical·HTTP 상태가 정상인지 확인한다.
4. 접근 가능한 경우 Search Console URL 검사로 실제 크롤링 결과를 확인한다. 검색 색인 자체가 AdSense 승인을 보장하지는 않는다.
5. 운영자가 콘텐츠와 계정 설정을 검토한 뒤 AdSense 사이트 검토를 요청한다. 승인 여부는 Google 판단이며 단순 설정 변경이나 글 수 증가로 보장할 수 없다.

## 5. 비용 작업과의 연결

우선순위는 Firestore 저장량 정리와 운영 점검 → 승인된 Spark 전환 → 교육 콘텐츠와 정적 페이지 개선 → 모바일 검증 → AdSense 재검토다. 콘텐츠 초안과 로컬 빌드 개선은 비용 정리와 독립적으로 진행할 수 있다.

기존 IAM·스케줄러·삭제/정리 작업 묶음은 자동 승인 검토에서 거절되어 해당 구체적 범위 승인이 별도로 대기 중이다. Spark 전환 승인을 그 작업 전체의 승인으로 확장하지 않는다. 현재 Spark 전환이나 유지보수 cron 설치가 완료된 것으로 보고하면 안 된다.
