- 실제 실행 루트: `/home/YOUR_SCHOOL_ID/mesugak/repo/Mesugak_V2`.
- Python: `/home/YOUR_SCHOOL_ID/micromamba-root/envs/py312/bin/python`, 3.12.13.
- 22:36 시점 이 계정의 MesuGak 상주 프로세스는 없음. 실시간 매매는 15:35 종료 후 다음 평일 크론으로 시작하는 구조이며, 짧은 크론 작업은 실행 사이에 프로세스가 없어도 된다.
- 마지막 대회 heartbeat: `session_complete`, 15:35:00, 보유 0, 미확인 주문 0, `reconciliationRequired=false`, `error=null`. `entryEnabled=false`는 이 장 종료 기록의 값이다.
- 마지막 세션 감시 39개, 고정 0·탐색 39개, 관측 시세 35,242건, 당일 점수를 관측한 종목 247개. 이는 현재 장외에서 감시 중이라는 의미가 아니다.

## 완료로 보면 안 되는 항목

### 첫 KIS 전체 검사는 아직 끝나지 않았다

`runtime/contest-kis-scan.json`은 오늘 **18:00:14에 `interrupted`**다.

| 지표 | 값 | 해석 |
|---|---:|---|
| 최초 목표 `totalCount` | 2,755 | 검사 시작 시 제외 목록을 반영한 종목 수 |
| 성공 `successCount` | 1,457 | 유효한 KIS 점수 산출 |
| 실패 목록 | 36 | 데이터·이력·요청 오류. 거래 불가 확정 목록과는 다름 |
| 상태 파일 `remainingCount` | 1,262 | 목표 − 성공 − 실패 계산값 |
| 현재 후보 파일 행 수 | 2,754 | 검사 도중 제외 종목이 추가되어 최초 목표와 1개 차이 |
| 후보 파일 미평가 `scorePending` | 1,261 | 점수가 0점이라는 뜻이 아님 |

실패는 `ValueError` 19건, `RuntimeError` 17건으로 기록돼 있다. 구체적인 의미는 해당 로그와 종목 이력을 함께 봐야 한다. 다음 장전 예약에서 재검사하지만 **08:50까지 모든 종목이 끝난다는 보장은 현재 없다**. 오늘의 첫 캐시 구축은 장중 12:15 시작했고 일시적으로 18:00까지 실행했다. 기본 장전 제한은 08:50다.

### 감시 39개와 실시간 점수 준비 39개는 다르다

마지막 heartbeat의 `scoreHistoryReadyCount=2`, 당일 누적 `observedScoreCount=247`, 마지막 감시 목록의 점수 표시는 비어 있었다. 교체 직후·장 종료 시점의 이력 준비 상태가 섞일 수 있어 `watchCount`만으로 전 종목 실시간 점수 준비를 판단하면 안 된다. 이력 준비를 기다리는 탐색 종목에는 최대 300초 유예가 구현돼 있지만, 마지막 기록만으로 처리 용량이 충분하다고 입증되지는 않는다.

### 학교 서버 프론트 소스와 실제 웹 배포본은 다르다

학교 서버에 남은 `frontend/`, `firebase.json`, `firestore.rules`는 로컬의 최신 파일과 차이가 있다. 학교 서버는 분석 작업 실행처이며, 그 폴더가 곧 현재 웹 화면의 배포본은 아니다. 실제 Hosting에서 받은 주요 HTML은 로컬 `frontend/dist`와 바이트 단위로 일치했다. 클라우드에 배포된 Firestore 규칙 전체와 모든 JS 청크의 동일성은 이번에 재검증하지 않았다.

### 대회 최대 보유 한도는 현재 3종목이다

서버의 환경 로더와 인자 파서를 읽기 전용으로 실행한 결과 `max_positions=3`이었다. 코드 기본값은 5지만 `.env.contest`에 해당 항목이 없어서 일반 `functions/.env`의 `MESUGAK_MAX_POSITIONS=3`을 상속한다. 종목당 목표 비중은 20%다. 과거의 “20%씩 5종목” 설명과 현재 실효값이 일치하지 않으며, 이번에는 매매 설정을 변경하지 않았다.

### 클라우드 함수가 전부 삭제된 상태는 아니다

Firebase 목록에는 V1 `refreshPendingOrdersFromBuySignals=ACTIVE`, `scheduled_paper_flow=FAILED`가 남아 있다. 전자는 로컬 V1 소스상 분석의 `buy_signal`을 `pending_orders`로 옮기는 작업이며 직접 KIS 주문을 넣지 않는다. 실제 배포 소스 동일성·최근 호출 여부는 미확인이다. Cloud Scheduler API는 결제 미활성화 사유로 403이어서 예약의 현재 ENABLED/PAUSED 상태는 확인하지 못했다.
