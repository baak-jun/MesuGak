## 2. 복사 범위와 제외 항목

배포된 V2의 Python·shell·프론트 텍스트 소스·설정 예제·문서·테스트를 확장자 허용 목록으로 가져왔다. 서버 원본은 수정하지 않고 SSH 표준 출력으로 생성한 tar 스트림을 로컬에 저장했다. 인증 env 파일은 이름과 비민감 설정만 별도로 추출했다.

다음은 실제 내용을 복사하지 않았다.

- `.env`, `.env.contest`, `.env.server` 등 실제 인증 환경 파일, 서비스 계정 JSON, SSH 개인키, KIS token.
- 운영 SQLite 원장·WAL 원본, 메일 본문·인증 응답 원문. 스키마·행 수·허용된 상태만 추출했다.
- 전체 시세 캐시·대용량 분석 checkpoint·원시 로그·과거 백업/배포 staging의 내용. 파일 경로와 크기 등은 inventory에 포함했다.
- `.git`, `node_modules`, `venv`, `.venv`, Python cache 등 재생성 가능한 의존성 트리. 이 디렉터리는 inventory 순회에서도 제외했다.
- 바이너리 이미지 등 허용 텍스트 확장자 밖의 파일, 8 MB 초과 파일, UTF-8로 읽을 수 없는 파일, 심볼릭 링크 대상.
- 공용 학교 서버의 다른 사용자 홈·관리자 전용 파일.

따라서 이 자료는 **운영 소스와 구조를 이해하기 위한 복사본**이며 서버 전체 디스크 이미지나 즉시 기동 가능한 인증 포함 백업은 아니다. inventory가 운영 파일을 포함해도 그 파일 내용이 모두 압축본에 있다는 뜻은 아니다.

민감값이 제거됐어도 파일 경로·시스템 구성·종목 감시 기록 등이 있는 내부 운영 자료다. 공개 웹 정적 파일 디렉터리에는 넣지 않았으며 Git 추적에서 해당 스냅샷 디렉터리만 제외한다.

## 3. 로컬과 서버 차이

V2 141개 파일의 비교 결과:

| 상태 | 수 |
|---|---:|
| 원격 SHA-256과 완전히 동일 | 68 |
| CRLF/LF 줄바꿈만 다름 | 43 |
| 내용 차이 | 25 |
| 민감값 마스킹 때문에 추가 수동 비교 필요 | 5 |

비교 시점은 새 운영 문서를 기존 README에 연결하기 전이다. 이후 링크를 추가한 문서는 당연히 서버 사본과 달라질 수 있다. 동일성 여부는 그 당시 비교 기록이며 향후 수정 후에도 같다는 보장은 아니다.

대회 핵심 Python 실행 파일과 공용 엔진은 원본 동일 또는 줄바꿈 차이로 확인됐다. 주요 내용 차이는 오래된 학교 서버 프론트·Firebase 설정·규칙·과거 문서에 있다. 수정 중인 로컬 파일을 서버 사본으로 덮어쓰지 않았다. `FILE_INDEX.md`와 비교 JSON에서 개별 경로를 찾을 수 있다.

## 4. 복구 시 구분해야 할 자료

| 자료 | 복구 원칙 |
|---|---|
| Python·shell 코드 | 문제가 난 변경 범위만 비교하고 검증된 버전으로 되돌린다 |
| 인증 env·service account | 현재 권한을 유지하는 별도 보안 백업에서 복원한다. 마스킹 예제로 덮어쓰지 않는다 |
| 대회 SQLite | 현재 증권사 주문·잔고와 대조할 핵심 기록. 이전 원장으로 단순 덮어쓰기 금지 |
| SQLite WAL/SHM | 실행 중 파일 일부만 복사하면 일관성 문제가 생길 수 있다. SQLite backup API로 일관된 백업을 만든다 |
| 최고가·부분 매도 상태 | 포지션·원장과 함께 보존. 초기화하면 매도 기준이 달라질 수 있음 |
| KIS 일봉·공공데이터 캐시 | 재생성 가능하나 첫 캐시 구축에 시간이 걸림 |
| cron | 필요한 줄만 비교. 과거 전체 crontab으로 교체하면 새 메일·검사 예약을 잃을 수 있음 |
| 최신 웹 | 학교 서버의 오래된 frontend가 아니라 확인된 최신 로컬 소스·빌드·Hosting 결과를 기준으로 함 |

서버의 `/home/YOUR_SCHOOL_ID/mesugak/backups/`에는 과거 배포 전 백업이 있다. 정확한 하위 경로는 inventory에서 `backups/`로 검색한다. 백업 안에는 실제 env나 원장이 있을 수 있어 이번 코드 복사본에 통째로 넣지 않았다.

원장 백업이 필요할 때는 매매 상태를 먼저 확인하고 승인된 비공개 목적지에 SQLite backup API로 저장한다. 복원은 실행 중 프로세스·미체결 주문·브로커 잔고를 먼저 확인한 후 진행해야 한다. 이번에는 복구나 중단을 실행하지 않았다.

## 5. 검증과 남은 확인 범위

- 원격 스냅샷의 모든 소스 복사본에 대해 manifest SHA-256을 검증했다.
- 압축 무결성, 문서 내부 링크, 파일 색인 수, 금지된 인증 파일 포함 여부를 확인했다. 검증 결과는 `validation.json`에 보관했다.
- 실제 서버 환경을 로드한 파서의 비민감 실효값을 따로 확보했다. 코드 기본값 5와 실제 최대 보유 3의 차이를 확인했다.
- Hosting 주요 응답은 로컬 dist와 비교했다. 로그인·Firestore 규칙 배포 버전·모든 웹 상호작용은 재검증하지 않았다.
- `systemctl --user`는 사용자 DBus 부재로 조회하지 못했다. Cloud Scheduler는 결제 미활성화로 403이었다. 이것을 “서비스/예약이 0개”로 적지 않았다.
- 운영 코드 수정이 없으므로 매매 테스트·재시작·신규 주문을 검증 목적으로 실행하지 않았다.

문서의 점수·보유·진행률은 표기 시각의 스냅샷이다. 이후 운영 판단에는 서버의 최신 timestamp와 실제 계좌 조회를 사용한다.
